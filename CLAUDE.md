# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Nuottipeli ("note game") is a music note recognition trainer. It displays notes on a treble clef staff and the player identifies them by pressing the corresponding letter key. The app is entirely in Finnish.

## Development

No build step, no package manager. Open `index.html` in a browser to run — though the instrument recordings in `sounds/` are fetched, which a browser only allows over HTTP, so off the disk the app falls back to its synthesised tone; `vite . --port 3000 --host` is what is used in development. The entire app is three files plus those recordings, the vendored code and fonts, and the listening game's photographs in `images/`:

- `index.html` — markup, loads VexFlow from `vendor/vexflow.js`
- `script.js` — game logic, audio synthesis, theme system
- `styles.css` — themes (via CSS custom properties + `data-theme` attribute), layout, animations

## Architecture

**No CDN**: nothing is loaded from another server. VexFlow is vendored as `vendor/vexflow.js` (the unmodified 4.2.5 `cjs` build, MIT) and the two typefaces, DM Sans and DM Serif Display (OFL), are in `fonts/` with their `@font-face` rules at the top of `styles.css`. Each folder has a README saying where its files came from and under what licence; the licence texts sit beside them, which both licences ask for.

**Notation rendering**: Uses VexFlow 4.2.5 (vendored) to draw notes on an SVG staff. The visible window scrolls forward as the player progresses, keeping a few past notes visible for context (`CONTEXT_BEHIND`). Note colors (past/current/future) come from CSS custom properties read at render time.

**Audio**: Web Audio API throughout. Notes are played off recordings of the instrument picked in the settings — `INSTRUMENTS`: piano (the default), acoustic guitar, clarinet — kept under `"instrument"` in `localStorage`. The recordings are per-note MP3s in `sounds/<id>/` from the FluidR3_GM soundfont (CC BY 3.0, credited in `sounds/README.md` and the README, which the licence requires). Only every third semitone is there, A1 through Es6 — 19 files an instrument, covering everything the clefs, the key chords and an altered interval can ask for — and `playSample()` plays the nearest one a semitone fast or slow at most. `startSample()` is the layer under it, taking any instrument and returning its nodes so the listening game can play its own and cut them short. `loadInstrument()` fetches and decodes a set once (on an `OfflineAudioContext`, so loading at startup does not open the real context before a gesture) and `sampleOnset()` finds where each recording actually starts, since an mp3 opens with a little silence that would put a note behind its picture. Everything still goes through `playTone(freq, duration, delay, gain)`, which tries the recordings and otherwise synthesises the note — layered sine oscillators with an exponential decay, the app's original sound — so the first note before a set has loaded, a failed download, and a page opened off the disk all still make a sound. Each instrument has a `level` (the recordings are quiet and not equally so) and a `sustain`: a clarinet holds its note where a piano's dies away, so it is given only part of the asked-for length or the interval climb's rungs smear together. The picker is `#instrument-menu`, under the language list in the settings dialog's first column and sharing `.lang-menu`'s rules; `applyInstrument()` answers a pick with a note once the set is in. Instrument names are translated (`instrument.<id>`). Error feedback is still a synthesised dissonant sawtooth pair whatever the instrument.

**Note naming**: Nordic convention — the note B is called "h" (accepts both "h" and "b" as correct input). Shared by both UI languages, so the plain letters are never translated. Key names are the exception: Finnish and Swedish spell the altered degrees differently (Es/Ess, As/Ass, Fis/Fiss), so those live in `STRINGS` under `key.<id>` like any other translated string, and the relative minor sharing each signature under `key.<id>.minor`. A signature belongs to two keys, so `keyName()` names it as both — "C-a", "Des-b" — major uppercase and minor lowercase, which is the Nordic convention and the whole of the distinction. Both halves are translated, since Swedish spells the altered degrees Ass, Ess, Fiss.

**Language**: Finnish (default) and Swedish. Every user-visible string lives in `STRINGS` in `script.js`, keyed identically per language, and is read through `t(key, vars)` (`{index}`-style placeholders; a missing key falls back to Finnish). Static markup keeps its Finnish text plus a `data-i18n="key"` (textContent) or `data-i18n-aria="key"` (aria-label) hook. `applyLanguage()` translates the static text and rebuilds every JS-drawn menu; the builders mark their own active entry, so selections survive the rebuild and a running game is not restarted. The choice persists in `localStorage` under `"language"`. Clef and theme entries carry no `label` field — their names are looked up as `clef.<id>`, `theme.<id>`.

**Note ranges**: Which notes appear is the player's only difficulty knob — there are no levels. The settings dialog's "Nuottialue" section sets an explicit lowest/highest note from the current clef's pool, and `activeNotePool()` crops the pool to it. The choice is stored per clef in `localStorage` under `"noteRanges"` as `{ "<clefId>": { low, high } }`; anything missing or naming notes the clef lacks falls back to `defaultRange()` — a band of `DEFAULT_SPREAD` diatonic steps around the clef's middle staff line, i.e. one ledger line either side. `loadRanges()` migrates the older per-level shape (`"<clefId>:<difficultyId>"`, the levels being easy/medium/hard) by keeping the level that used to be the default, and writes the migrated shape back. The range is shown by the highlighted notes, by `.range-band` — a band drawn across them — and by `.range-letters`, the pool's note names spelled out under the staff with the in-range ones in the accent colour. The letters are what make a range readable without naming the notes off the staff first, which is the skill the game is for rather than a toll to pay in settings; each nudged `NOTEHEAD_HALF_WIDTH` (8.5px, measured off the drawn heads rather than guessed) to the right, because `getAbsoluteX()` reports a note's left edge rather than the middle of its head. `noteCentreX()` is that nudge, and everything laid over the staff — the letters, the band's edges, the ghost — is placed through it: measuring a band edge from the raw x instead put the low end a notehead further out than the high end, which read as one end floating in the gap and the other clamped to its note. `bandPad()` then spreads each edge half a gap from its notehead's centre, so it falls midway to the next note — the same line the hit columns divide on. It is floored clear of the notehead (the columns on a phone are narrower than the heads standing in them) and capped at the room past the last note's centre, which `STAVE_INSET` and `POOL_STAFF_TRAILING` name in `drawPoolStaff` rather than leaving the band to hang off the staff and the dialog to grow a sideways scrollbar for it. They are a sibling of `.range-staff` rather than a child, since the band and the hit areas are absolutely positioned across the staff's full height and would sweep letters inside it under both. They are `aria-hidden`, because the `.range-hit` buttons already carry every note's name and whether it is in range. Still no octave numbers anywhere — the staff says which octave. Every clef's `notePool` spans the same geometry — nine diatonic steps below its middle line through eight above, i.e. 18 notes with two ledger lines either side — so a range covers the same span of notes whichever clef is showing.

**Setting a range**: the whole staff is the control. A press grabs whichever end of the range is nearer (a range collapsed onto one note opens toward the pressed note instead), and sliding drags that end from note to note; it stops at the other end rather than crossing it. Only the band moves during a drag — the staff is redrawn once, on release, by `commitRange`, which also drops an edit that changes nothing. This matters on a phone, where a note's column is only ~15px wide: the player aims with the band, not with the column. A mouse also gets a preview of the press it is about to make: `.range-ghost` draws the band's whole edge again — the line up the full height of the staff, the curve away at either end, the grip across the middle — in the faded `--note-future` grey, at the note the nearer end would land on, including where it stops short of the other end, and nothing at all where a press would change nothing. Being one end of a band rather than a band, it carries its border down one side only and the radius on that side's two corners; `data-edge` says which side, so the same element serves both ends and the grip hangs off the bordered one. Its width is that radius — the room the curve needs — mirrored from `styles.css` in `RANGE_GHOST_WIDTH`, and `ghostPlacement()` lines the bordered side up with where the band's edge would be, so the ghost lands on the same pixels as the edge it stands in for. It is drawn for the mouse only — the handler ignores every other `pointerType` and the styles only give it a `display` inside `(hover: hover) and (pointer: fine)`, since a finger has nowhere to hover and a preview lit by a tap would only be left behind under it. It is hidden while a drag is running (the band is the thing to watch by then) and re-placed at the end of `renderRangeStaff`, since a redraw usually follows an edit made with the mouse still on the staff. `.range-staff` is `touch-action: pan-y` so a vertical swipe still scrolls the dialog, and a gesture the browser takes over arrives as `pointercancel` and is rolled back. The `.range-hit` buttons remain one per note for the keyboard and for screen readers; the click handler behind them takes only keyboard activations (`event.detail === 0`), since a press has already applied itself by the time its click arrives.

The range staff is drawn only once it has a width. Drawing it at a fallback width while the dialog is still `hidden` widened the grid track it sits in, and the redraw on open then measured that inflated track instead of the dialog — which pushed the staff off the side of a phone screen.

**Screens**: `showScreen()` swaps between the app's sections. `#menu-screen` is the start screen and the hub. It carries no heading of its own — the two group labels say what is on it, and a title above them would only repeat the browser tab. One entry per *thing* the app does (`.menu-item`: an icon, a name, and a line saying what it is for), and every other screen has a way back to it: `.toolbar-back`, at the left of the toolbar opposite the settings gear, shown on every screen but the menu (the gear is pushed to the right by a `margin-left: auto` of its own rather than by the toolbar's justification, so it keeps the same corner on the menu screen, where it is the row's only child) — `showScreen()` toggles it, and like the gear it sets a `display` of its own, so `.toolbar-back[hidden]` has to spell the hiding out. It replaced a "Takaisin" button at the foot of each screen, which the games and the results never had. Escape is deliberately *not* the same: it steps out of the setup, cards and chart screens but leaves a running game alone, since a stray Escape should not walk out of a half-finished round while a deliberate click may. "Tunnista nuotit", "Tunnista sävellaji" and "Tunnista intervalli" all lead to `#setup-screen` — the shared round-length picker — and "Nuottikortit" to `#cards-screen`. The settings are not among them: they stay behind the toolbar gear, which is on every screen including this one, so the menu lists things to play rather than mixing them with configuration. Escape steps back one level: the dialog first if it is open, then out of the cards or setup screen to the menu. A running game is deliberately left alone — there is no half-finished round to walk out of by accident.

`.main-menu` is three columns: notes, keys, and a third shared by intervals and instruments, each subject a `.menu-group` with its own heading. The third column holds two subjects with one game each — `.menu-group-upper` in the grid's top two rows, `.menu-group-lower` in the bottom two — rather than a fourth column the 720px card has no room for; the lower heading falls in a row as tall as the entries beside it, so it is `align-self: end`, against the entry it belongs to. Both carry an explicit `grid-column`, which the stacked layout below 760px resets along with the rows. Grouping by subject rather than by kind of activity means the pairing reads down a column — game, cards, chart — instead of across; the intervals column holds only the game so far, and is a column rather than a fourth entry under Nuotit so that what it gains later has somewhere to go. Three columns inside the 720px card leave each about 210px, close to what two of them came to on the narrowest screen that still showed two. Below 760px the groups stack, headings and all. The markup is grouped the same way, so an entry belongs to a column by where it sits rather than by counting grid cells. The columns are **subgrids** of `.main-menu`'s rows rather than three stacks sizing themselves, so an entry is as tall as the tallest entry beside it: a description that wraps to one more line than its neighbour used to drop everything below it in that column out of step, which Swedish reached first — "Alla tonarter på en gång." takes two lines where the notes column's takes one. The row count is the longest column's entries plus its heading, so a fourth entry in a column means a fifth row. Stacked, the query undoes both the spans and the shared rows, and it sits *below* the `.menu-group` rule it overrides rather than above it, since the two match on specificity.

**Four games, shared parts**: `gameMode` (`"notes"` / `"keys"` / `"intervals"` / `"listening"`) says which round is running. They share the counters (`correct`, `wrong`, `streak`, `currentIndex`, `totalNotes`), the results screen, and the round-length picker, so nearly everything that touches a running game dispatches on it: `beginGame` picks the screen and the start function, `updateStatus` writes through `statusElements()` to whichever screen's status block is showing, `redrawCurrentGame()` stands in for `renderNotation()` wherever a redraw is wanted (theme, clef, language, resize), and the keydown handler routes letters to the note game and number keys to the other two. `statusElements()` is a table keyed by `gameMode` (`STATUS_BLOCKS`) rather than a chain of ternaries, which stopped reading as one at three. `showSetup(mode)` sets the mode and swaps the title's `data-i18n` key, so a language change re-translates the right string. Note that `showSetup` takes an argument — a listener passed it directly would hand it a click event as the mode.

**Key signature game**: `#keys-screen`. A staff carrying only a clef and a key signature, and four answers to pick from; `KEYS` is the fifteen major keys from seven flats to seven sharps, with VexFlow's key spec (`vf`), the signed accidental count, and the tonic a right answer sounds. `keyChoices()` draws the three wrong answers from the signatures *nearest* the right one on the circle of fifths — picked from the whole circle they would mostly be a giveaway, since telling four sharps from six flats needs no reading. A question keeps its four answers while it is unanswered, so `keyQuestions[i]` holds both. The options are answered by clicking, or by 1-4 counting along them from the left — the numbers are deliberately not drawn on the buttons, being four more things to read on a screen already asking one question, so the shortcut is there for whoever finds it rather than advertised. A wrong pick is counted and costs the streak but does not advance, exactly as in the note game, so accuracy measures tries rather than skips. A right one is *held*: the signature stays on the staff with the answer lit beside it for `KEY_REVEAL_HOLD_MS` before the next question is drawn, so the two chords it sounds are heard over the signature that earned them rather than under the one after it. The wait is measured off `TRIAD_GAP_SECONDS` — the front of the second chord plus enough of it to be heard as one — so the picture and the sound cannot drift apart. `keyHold` is that pause, and like the interval game's climb it holds the round still: `currentIndex` does not move until `finishKeyHold()`, so the progress line, the staff and a redraw landing mid-hold all say the same thing. Any answer press during it cuts it short and moves on, the bargain the climb and the card deck's reveal timer both make, and `showScreen()` cancels one left behind.

The staff is sized to its content: a probe `Stave` that is never drawn reports `getNoteStartX()`, and the real one is that plus `KEY_STAVE_TRAILING`. A staff sized for seven accidentals would leave C major — a legitimate question, and a bare staff — floating in an empty field. The accidentals are tinted with `--note-current` through VexFlow's `.vf-keysignature` group, since they are what the player is being asked to read. `noteFrequency()` was widened to parse accidentals (`f#/4`, `bb/4`) so a tonic can be sounded. A right answer sounds the two keys the name reads — the major triad, then the relative minor one `TRIAD_GAP_SECONDS` later — through `playKeyTriads()`. Those are built from semitone offsets off the major tonic's frequency (`MAJOR_TRIAD`, `MINOR_TRIAD`, `RELATIVE_MINOR_SEMITONES`) rather than from note keys, because the spellings are the awkward part: the third of a Cis major triad is Eis. `playTone()` is the bare oscillator stack, taking a frequency and a gain — turned down for a chord, three notes sounding at once — and `playPianoNote()` is now the wrapper that looks a note key up in it.

**Listening game**: `#listening-screen`, "Tunnista soitin". An instrument is heard and four are shown, each a photograph over its name; the one that was playing is the answer. The question is the sound alone, so the options can carry both picture and name without giving anything away. `LISTENING_INSTRUMENTS` is the twenty-two of them. Each has a `voice` — an entry shaped like `INSTRUMENTS`' (`id` naming its folder in `sounds/`, `level`, and `low`/`high` bounding the seven recordings it has, an octave and a half) — except that the flyygeli, guitar and clarinet point at the settings' own instruments, so those recordings are shared, and the theremin has none: `startTheremin()` synthesises it, one oscillator whose pitch *slides* between notes with a slow vibrato, which is what a theremin is. `held` marks the blown, bowed and squeezed instruments, whose notes are given exactly their beats; a struck or plucked one rings `LISTENING_RING_SECONDS` past them. `twin` names an instrument never offered in the same four: piano and flyygeli, which no one tells apart by a soundfont, and a question that cannot be answered by listening has no business here.

What is played is one of `LISTENING_PHRASES` — short figures inside an octave, none of them a known tune — started on a random note within `LISTENING_ROOT_SPREAD` semitones of the instrument's lowest, so what is recognised is the instrument and not the phrase. A question keeps its phrase and its four answers (`listeningQuestions[i]`), so a replay is the same thing again. `playListeningQuestion()` waits for the recordings (`loadInstrument()`; `ensureListeningQuestion` starts the fetch when the question is built, and `renderListeningRound` builds the next one too, so only the very first can be late) and drops the phrase if the round has moved on meanwhile. Whatever is still sounding is kept in `listeningVoices` and cut by `stopListeningSound()` when the next phrase starts or `showScreen()` leaves — otherwise a quick answer lays one instrument over the tail of another. Where the other games have a staff there is `.listening-stage`, the same framed area holding the replay button, so the feedback animations have the same thing to act on. Answered by clicking or 1-4; Space replays. A wrong pick is counted and shakes; a right one is lit for `LISTENING_HOLD_MS` (`listeningHold`, the key game's arrangement, cut short by any answer press) and then the next is played. `redrawCurrentGame()` only redraws the choices, so a theme or language change does not play the phrase again, and `restartRound()` does nothing: no clef is involved. `beginGame` sets `gameActive` *before* `startListeningGame()`, since the first phrase is played from in there and checks it.

The photographs are `images/<id>.avif`, from Wikimedia Commons, each fitted to 480px and flattened onto white; `images/README.md` credits every one, which their licences require (several are CC BY-SA). They sit `object-fit: contain` in a white square whatever the theme — a flute is five times as wide as a tuba, and a photograph's background is not the palette's to recolour. `startListeningGame()` asks for all of them up front so a card's picture does not arrive after its name. The instrument names are `listen.<id>`, separate from the settings' `instrument.<id>` because the two lists name things differently ("Akustinen kitara" there, "Kitara" here).

**Interval game**: `#intervals-screen`. Two notes on a staff in the clef and range already set, and the distance between them to name. The answer is a number — priimi, sekunti, terssi and the rest *are* numerals — so the pad below the staff carries the eight of them in their own order and never in any other, and the number key that answers one is the number written on it: press 5 for a kvintti. That is the difference from the key game's four choices, which reshuffle every question: an interval's name is not one of four things it might be, it is a count, so the answer sits in the same place every time and the pad reads as a keyboard rather than a quiz. Unlike `.note-pad`, which is a touch-only stand-in for letters that can be typed, the pad is on screen everywhere, because the *name* under each numeral is half of what is being learned.

The number only, never the quality: counting the lines and spaces is the skill this app is for.

**Which intervals**: the round-length picker carries three radio buttons for this game only (`#interval-scale`, shown by `showSetup()` when the mode is `"intervals"`): "Duuriasteikkoiset intervallit", "Kaikki intervallit" and "Supertietäjä". The choice is `intervalScale` (`"major"` / `"all"` / `"super"`), persisted under `"intervalScale"`, major being the default. It reuses the card deck's `.card-order` pill and its buttons; `.interval-scale` only adds the `[hidden]` rule the pill's own `display` needs and lets the two long labels share a phone's width. "All" keeps the signature and adds an accidental of its own to the upper note, so the minor, diminished and augmented intervals come up too. `randomTopAccidental()` picks the upper note's pitch from flat, natural and sharp, keeping only those within a semitone of the scale degree the signature gives it: a note the signature leaves alone comes out flat, sharp or as it is, and one it sharpens or flattens is either left or put back with a natural sign — never a double accidental, and never a doubly diminished or augmented interval. A priimi is never lowered, which would put the "upper" note under the one the staff is signed in. The pick is equal among what is left, so the unaltered scale degree stays one of the answers and "all" still includes the major-scale intervals. The question carries it as `top: { sign, alter }` — `sign` is what VexFlow draws (null where the pick is what the signature already says), `alter` the semitones off the scale degree, which `intervalTopFrequency()` sounds — so the drawing and the sound read it off the question rather than off the setting. The accidental is an `Accidental` modifier in `--note-current`, handed a `ModifierContext` by hand since no `Formatter` runs here, and during the climb the travelling note only wears it on the last rung: the rungs on the way are plain degrees of the scale. The played-through marks are shared between the two, being kept per game. "Supertietäjä" is "all" without the key signature: the staff carries only the clef, and every note wears the accidental it actually needs in front of it — the lower note whatever the signature would have done to its letter, the upper one that plus its own `top.alter` — through `intervalNoteSign()`. Since the upper note never ends up more than a semitone off its natural, a sharp or a flat is all either note ever needs; no naturals are written, there being no signature to cancel. During the climb each rung wears its scale degree's accidental the same way. The question carries `bare: true`, so a redraw draws it as dealt whatever the setting has become since. It asks for the quality like "all" (`intervalAsksQuality()` is every round but a major-scale one), and the sound is unchanged — the key is still there, only not written. A major-scale round also names the quality on the pad — "puhdas priimi", "suuri sekunti" — since each size has exactly one there (`MAJOR_SCALE_QUALITIES`, the words under `interval.perfect` / `interval.major`); a round of all the intervals keeps the bare names, a terssi there being either kind. `startIntervalsGame()` rebuilds the pad for that reason, and below 560px `.interval-option-quality` takes a line of its own so the boxes stay the same height.

**Two halves of an answer**: a round of all the intervals asks for the quality as well as the number. `#interval-qualities`, a row above the pad built by `buildIntervalQualities()` (called from `buildIntervalOptions()`, so it follows every rebuild of the pad) and hidden in a major-scale round, carries puhdas, pieni, suuri, vähennetty and ylinouseva (`INTERVAL_QUALITIES`, words under `interval.<quality>`). A quality is *picked* — it stays lit, `pickedIntervalQuality` — and the number then commits both, so the number key is still what answers. A number with nothing picked is not counted: the row shakes and lights (`.nudge`) until something in it is chosen. `intervalQuality(question)` is the right one, from the size's quality in the major scale and `top.alter`. A wrong answer is one mistake however many halves were wrong, but each wrong half shakes; a wrong quality is let go of, a right one stays picked for the next try at the number. The pick is cleared in `finishIntervalWalk()`, so the right answer stays lit through the climb. The digits being taken, ←/→ walk the pick along the row; picking during a climb cuts it short like an answer key does. Below 560px the five sit three and two.

**The signature**: every question's staff, in either kind of round, opens with the key signature of the *lower* note's major scale — which is always the first of the two — so d→a is read as 1→5 of D major. The pool notes are all naturals, but the signature is what spells the tonic — a note on the h line under two flats *is* a b, with nothing written beside it — so the lower note can be an altered one without the pool holding any. `intervalKeysFor(letter)` lists the keys a note on that letter may be the tonic of: the natural's own key always (however many accidentals it takes; H major has five), plus every flattened or sharpened tonic written on that letter — B, Es, As, Des, Ges, Fis, and the two keys of seven, Ces and Cis. `question.key` is the `KEYS` entry drawn from that list and `question.tonic` the written note; `intervalFrequency()` moves the tonic by `signatureAlteration()` of its own letter before counting up the scale. It is tinted `--note-future` through `tintKeySignature()`: it is context for the two notes, not the thing being asked about, so it is fainter than they are. The sound follows the staff: `intervalFrequency()` sounds each note as the degree of the tonic's major scale it sits on (`MAJOR_SCALE` semitones off the tonic's frequency, as the triads are built), so a g over e under four sharps sounds gis — in a major-scale round every interval heard is therefore a major or a perfect one. The staff is sized to its content, so it is wider under five sharps than under none; the probe stave carries the signature too.

`makeIntervalQuestion()` draws the size first and fits the notes to it, rather than drawing two notes and reading the size off them — a pool holds far more pairs a sekunti apart than an oktaavi, so the second way leans hard toward the small intervals. It keeps the whole `ladder`, every note from one end to the other and not just the two that are written, because the rungs are what the reveal climbs; a pool is a run of consecutive diatonic steps, so they are simply the slice between them. The lower note is always written first — an interval is counted up from its bottom note, and the signature names that note's scale — so no question reads downward. `availableIntervalSizes()` caps the sizes at the pool's length, so a range cropped to five notes tops out at a kvintti and the game stops asking rather than posing a question with no answer — the same bargain `availableMelodies()` makes with a clef too narrow for a tune. Both notes wear `--note-current`: neither one is the answer, the gap between them is, so there is no past and future to tell apart. The two are placed by hand through their own `TickContext`s, the way the range editor's are — a `Formatter` given two notes and a width crowds them both against the clef and leaves the rest of the staff empty.

**The climb**: a right answer is answered back with the count itself. The second note drops onto the first — both on the same line, which is what a priimi looks like — and climbs a rung every `INTERVAL_WALK_STEP_MS`, sounding each note it lands on, with the running count written beside it: 1 where they are level, 5 when it has got back to where it was written. The last rung is held for `INTERVAL_WALK_LAST_NOTE_LENGTHS` (2) rungs' worth — its sound and the wait after it both — since the note the climb arrives on is the one the count was for (`intervalWalkLengths()`; a priimi's single rung is its last). Then the two sound together, so the count just made lands as the sound of the interval, and the round moves on. One numeral that travels with the note rather than a ladder of them left behind, because consecutive rungs are five pixels apart — a column of numbers that close together is a smudge, not a count.

`intervalWalk` holds the question being revealed and how far it has got, and it holds its own question rather than reading the round's, because `currentIndex` does not move until the climb is over — the progress line should still say which interval is on the staff. `finishIntervalWalk()` is where the round actually advances, whether the climb was watched through or cut short: any answer key or a tap on the pad ends it early and moves on, the same bargain the card deck makes with its reveal timer, so nobody who has already read it is held up. `showScreen()` cancels a climb left half-finished, next to the card deck's pending advance, and `startIntervalsGame()` clears one before dealing a new round.

**Melodies**: The round-length picker offers, under a heading of their own, seven rounds that are a tune rather than a number — all out of copyright, and all named in both languages under `melody.<id>` with their origin under `melody.<id>.source`. `MELODIES` stores each as offsets in diatonic steps from the note it opens on, paired with that note's length in beats, plus `opensOn`, the letter of the note at offset 0. An offset of `null` is a rest (Kulkuset and Piippolan vaari have them): it is not a note to name, so it never reaches the staff and never counts toward `totalNotes`. They are listed narrowest span first and then shortest — the span is what makes a tune hard to read, so the list runs from Maijall' oli karitsa (five steps, 26 notes) to Jaakko kulta (nine, 32) — which is why Oodi ilolle is no longer first.

`melodyNotes(clef, melody)` places one in whichever clef is showing — the octave that puts its opening note nearest the middle staff line, of those the clef's pool can hold. **Whole octaves only**: every note of every tune is a natural and no pool has accidentals, so shifting one by anything else would change the tune rather than transpose it. Since every clef's pool spans the same 18 notes and the widest tune spans nine, all seven fit every clef today; `availableMelodies(clef)` still filters, so a narrower pool would drop a tune from the picker rather than show it dead, and `beginMelody` returns false so `restartRound()` and the Tab replay can fall back to a plain round instead of leaving one half-started.

`melodyRound` is `{ melody, entries }` while such a round is running and is what tells it apart afterwards — Tab on the results screen replays the same tune rather than a count, and `restartRound()` re-places it when the clef changes. The beats are a record of the tune and nothing reads them: the staff draws every tune as plain quarter notes like any other round, and a finished tune is deliberately not played back — the player has just played it. A tune is marked played under its own id rather than its length: 30 is one of the presets, and finishing Oodi ilolle should not tick it.

**Played-through marks**: The round-length picker ticks the lengths already played to the end, per game, from `playedCounts` in `localStorage` (`{ "<gameMode>": [id, ...] }`, an id being a length or a melody's id — `"ode-to-joy"` predates the other tunes and keeps working because the id it was stored under is still that melody's). `endGame()` records it, so an abandoned round does not count — the marks say what was finished, not what was attempted. `buildNoteCountOptions()` is rebuilt on every `showSetup()` (the marks differ per game, and the round just finished has to show) and on a language change (the marked buttons carry a translated `aria-label`); `buildMelodyOptions()` is rebuilt on a clef change too, since which tunes are on offer follows the clef and the dialog opens over the picker. The tick carries the meaning and the colour only backs it up, so the two states stay tellable apart without seeing the difference.

**Reference charts**: Two lookup pages rather than games, both following the clef picked in the settings. Neither names that clef in words: every staff on both pages carries the clef glyph itself, so a line saying "G-avain" over a page of treble staves is a caption on something already in plain sight. `#note-chart-screen` puts the current clef's whole `notePool` on a staff with every letter lit (it is a table, so nothing is picked out) — the range is deliberately ignored, since this answers "what are the notes" and not "what will the game ask". `#key-chart-screen` draws all fifteen signatures as tiles, grouped the way one is actually looked up: the sharp keys in order of how many sharps they carry, then the flat ones in order of their flats. Both columns start at C, which carries neither — a flat column opening on one flat would read as though the counting started at one. Every tile is drawn on a canvas sized to `widestKeySignature()` for the same reason the key cards are — otherwise C major would come out as wide as seven sharps with its accidentals shrunk to match.

Both charts are drawn in **ink** — `--text` — rather than in the accent colour the games use: the accent means "this is the note (or the signature) you are being asked about", and a lookup page asks nothing, so noteheads, accidentals and note letters are all the same colour. That is what `.chart-letters` overrides `.range-letter.lit` for, and why `tintKeySignature()` is handed `--text` by the chart and `--note-current` by the game and the cards, whose fronts *are* questions.

**The note chart on a narrow screen**: eighteen notes across a phone leave each notehead about as much room as it is wide, so they run into one another and the letters collide. `noteChartRowCount()` takes the measured width less the room the clef takes on every row, divides it by `CHART_MIN_NOTE_SPACING` (30px — a notehead is ~17px, and this is that with air either side), and spreads the pool over as few staves as will give every note that spacing: one row wherever there is room for one, so a desktop is unchanged and only a phone splits. The rows are equal-length chunks and `drawPoolStaff` takes the chunk length as its `columns`, so a short last row keeps the spacing of the ones above it and simply stops early instead of spreading three notes across the whole staff. Each row is sized to its own notes, so a row that stays on the staff is not padded out to fit ledger lines it hasn't got — vertical room is the scarce thing on the screen this is for.

The note chart's staves are *measured*, so it has the same trap the range editor does: `showNoteChart()` renders after `showScreen()`, and the resize handler redraws it — which is also what re-splits the rows when the window changes width. Each row is appended to `#note-chart-rows` before it is drawn, since `drawPoolStaff` measures the element it is handed. The key chart's tiles are scaled by CSS and look after themselves. `redrawCharts()` is called from `applyTheme`, `applyClef` and `applyLanguage`, and is a no-op unless a chart is the screen showing.

`drawPoolStaff()` is what the range editor and the note chart share: it draws a list of notes across one staff, colouring each however the caller asks, and returns the noteheads' x positions and spacing — which is what the range band, the hit areas and the letters are all placed from. `renderNoteLetters()` is the shared letters row. Both charts reuse the `.range-*` class names for those parts, the way the clef and theme menus kept theirs; "lit" is the generic modifier that means in-range in the editor and simply "on" in the chart.

**Card decks**: Reached from the menu and left by "Takaisin" or Escape. `#cards-screen` serves two decks, chosen by `cardMode`: the clef's notes ("Nuottikortit") and the fifteen key signatures ("Sävellajikortit"). They work the same way — a staff on the front, a name on the back — so they share the screen, the flip, the stepping and the position line, and differ only in what is drawn and what is named. `cardDeck()` returns whichever list is showing; `showCards(mode)` swaps the heading's `data-i18n` key so a language change re-translates the right one. The hint is shared, because it describes the one key that works both decks rather than what is on the cards.

The deck can be dealt straight through or shuffled, chosen by the two buttons above the card (`#card-order`) and persisted under `"cardOrder"`. The choice works both decks, since the control sits on the screen they share. Shuffled asks what the note game asks: with no telling what is coming, there is a moment to name the card to yourself before turning it over. It is a shuffle rather than a draw — `cardOrder` is a permutation of positions into `cardDeck()`, so every card comes up once before any comes up twice — and `resetCardOrder(avoidFirst)` deals it afresh whenever the screen is opened, the order is changed, the deck underneath changes length, or a pass runs off either end; `avoidFirst` keeps a reshuffle from opening on the card just seen, which would read as the deck having stuck rather than as chance. `cardIndex` counts through the order and the order points into the deck, so `currentCard()` is what the flip sounds.

A deck is worked through with the space bar alone — there are no prev/next controls. `revealOrAdvance()` turns the card over, sounds it, and sets a `CARD_REVEAL_MS` timer that moves the deck on by itself; a press while the answer is up cancels that timer and steps immediately, so reading fast is never held up by it. A tap on the card does the same, for touch. The space handler calls `preventDefault()`: without it a card that has the focus would be activated a second time by the click a Space on a `<button>` leaves behind. It then drops `event.repeat`, the same guard the games use — a held Space would riffle through the deck several cards a second, each flipped and gone before it could be read. The `preventDefault()` stays above that guard, since the repeats it declines to act on would otherwise go on scrolling the page. `showScreen()` clears any pending advance, so a timer cannot fire onto a screen the player has already left.

The key deck runs outward from the middle of the circle of fifths — `keyCardOrder()` sorts by `Math.abs(accidentals)`, so C comes first and each card adds an accidental to the one before it, out to the sevens. Opening on seven flats would be teaching the hardest card first. `KEYS` itself stays in circle-of-fifths order, since that is what the table documents. Only the note deck can come out empty, so the "no notes yet" guard is note-only. Note that `showCards` takes an argument — a listener passed it directly would hand it a click event as the mode.

Each key card's front is drawn by `renderCardKeySignature()` on a canvas sized to the *widest* signature there is, measured off probe staves that are never drawn. Sizing each card to its own signature would blow a bare C major staff up to the same width as seven sharps, so the accidentals would shrink as the deck got harder; one shared canvas keeps the scale constant and lets C major be what it is — an empty signature. `scaleCardSvg()` is the step both decks share: a viewBox, no size of its own, and the inline size VexFlow writes cleared, so CSS decides how big the staff comes out.

**The note deck**: the deck is `activeNotePool()` — the current clef's pool cropped to the current range, so it is exactly the notes the game would ask about — shown **one card at a time**, big, with an arrow either side and a "Kortti 3 / 13" line beneath. `stepCard()` wraps at both ends, so no arrow is ever a dead end, and it rebuilds the card, which turns it face-up again: the next note is a new question, not the previous answer. The arrow keys leaf through the deck; Enter and Space flip, which the card gets for free by being a `<button>`. `cardIndex` survives a redraw (a theme change should not send the player back to card 1) and `renderCards` clamps it when the deck it indexes into gets shorter.

A card's front is a whole note on a miniature staff, its back the note's name; a press flips it (a CSS `rotateY` on `.note-card-inner`, faces hidden by `backface-visibility`) and plays the pitch — a key card, naming two keys, sounds the two chords instead. The back carries **letters only** — the Nordic name and, where the two differ, the international one, so `INTERNATIONAL_NAMES` maps `h` to `B` and the card reads "H / B". No octave number: the card answers "which letter is this", and a number would be a second question the game never asks.

The card staves are drawn at a fixed internal width of 150 and then stripped of their `width`/`height` — the attributes *and* the inline styles VexFlow writes alongside them, which otherwise outrank the stylesheet and pin the staff at 150px inside a card several times that wide — in favour of a `viewBox`, so CSS scales them to fill the card. That means a card can be built while the screen is still hidden; unlike the range staff, nothing here is measured. The geometry comes from `staffGeometry()` (the helper the range editor also uses) measured across the whole deck rather than the one note showing, so the staff keeps the same size and the same middle line from card to card instead of shifting under the player as they step through. Note colours are read from CSS at draw time and the deck follows both the clef and the range, so `redrawCards()` is called from `applyTheme`, `applyClef`, `commitRange` and `applyLanguage` — it is a no-op unless the deck is the screen showing.

**Settings dialog**: The gear button in the toolbar is the only always-visible control. It opens a centered modal (`#app-settings-menu`, with a backdrop) holding the language list, the instrument list under it, the clef list, the theme list and the note-range staff — all of them are set once and then forgotten, so none take up room during play. The first three sit side by side in `.app-settings-cols`. The clef and theme lists keep their `.clef-menu` / `.theme-menu` class names from when they were dropdowns of their own, and `.lang-menu` shares the clef list's rules. The sections have no visible headings — their names live on as `aria-label`s. The "← Valmis" button sits in `.app-settings-bar`, a sticky header at the top of the dialog, so it stays reachable without scrolling past the note-range staff. It is at the left of that header, wearing `.toolbar-back`'s shape and arrow: the dialog covers the toolbar, so it is the back button while it is open rather than a second control opposite it.

**Theme system**: 5 themes (2 light, 3 dark) defined as `:root[data-theme="name"]` CSS blocks. JS sets the attribute on `<html>`. The blocks are `:root`-scoped on purpose — a bare `[data-theme=…]` also matches any other element carrying the attribute, which redefines the whole palette on it; that is why the theme picker's buttons name their theme with `data-theme-id` instead. The picker's two group boxes follow the active palette like the rest of the dialog, so only their headings say which group is light and which is dark; each entry is previewed by `buildThemeChip()`, a miniature staff and note drawn in that theme's own notation colours, which `THEMES` repeats in a `chip` field since JS cannot read a palette it is not currently wearing. Theme choice persists in `localStorage` under key `"theme"`. Ids that are no longer in `THEMES` are mapped through `LEGACY_THEME_IDS` and the resolved id is written back, so each entry only has to outlive the browsers still holding it: `"dark"`/`"light"` predate the named themes, and `"nord"` was the id of `storm` (Myrsky / Storm) while it still carried the name of the palette it was drawn from.

**Input**: Keyboard only — single letter keypress triggers `handleGuess()`. No on-screen buttons for note input. A held key is dropped by `event.repeat` rather than by a timer: the auto-repeat of a leaned-on key would be counted as a wrong answer several times a second and could run a whole round out, while a delay long enough to stop that would also throttle someone answering fast. Releasing and pressing again always answers. The guard sits above all three games and the results screen's Tab replay, and the card decks apply it too.
