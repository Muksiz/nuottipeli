# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Nuottipeli ("note game") is a music note recognition trainer. It displays notes on a treble clef staff and the player identifies them by pressing the corresponding letter key. The app is entirely in Finnish.

## Development

No build step, no package manager. Open `index.html` in a browser to run. The entire app is three files:

- `index.html` — markup, loads VexFlow from CDN
- `script.js` — game logic, audio synthesis, theme system
- `styles.css` — themes (via CSS custom properties + `data-theme` attribute), layout, animations

## Architecture

**Notation rendering**: Uses VexFlow 4.2.5 (CDN) to draw notes on an SVG staff. The visible window scrolls forward as the player progresses, keeping a few past notes visible for context (`CONTEXT_BEHIND`). Note colors (past/current/future) come from CSS custom properties read at render time.

**Audio**: Web Audio API piano synthesis — layered sine oscillators with harmonics and exponential decay envelopes. No audio files. Error feedback uses a dissonant sawtooth pair.

**Note naming**: Nordic convention — the note B is called "h" (accepts both "h" and "b" as correct input). Shared by both UI languages, so the plain letters are never translated. Key names are the exception: Finnish and Swedish spell the altered degrees differently (Es/Ess, As/Ass, Fis/Fiss), so those live in `STRINGS` under `key.<id>` like any other translated string.

**Language**: Finnish (default) and Swedish. Every user-visible string lives in `STRINGS` in `script.js`, keyed identically per language, and is read through `t(key, vars)` (`{index}`-style placeholders; a missing key falls back to Finnish). Static markup keeps its Finnish text plus a `data-i18n="key"` (textContent) or `data-i18n-aria="key"` (aria-label) hook. `applyLanguage()` translates the static text and rebuilds every JS-drawn menu; the builders mark their own active entry, so selections survive the rebuild and a running game is not restarted. The choice persists in `localStorage` under `"language"`. Clef and theme entries carry no `label` field — their names are looked up as `clef.<id>`, `theme.<id>`.

**Note ranges**: Which notes appear is the player's only difficulty knob — there are no levels. The settings dialog's "Nuottialue" section sets an explicit lowest/highest note from the current clef's pool, and `activeNotePool()` crops the pool to it. The choice is stored per clef in `localStorage` under `"noteRanges"` as `{ "<clefId>": { low, high } }`; anything missing or naming notes the clef lacks falls back to `defaultRange()` — a band of `DEFAULT_SPREAD` diatonic steps around the clef's middle staff line, i.e. one ledger line either side. `loadRanges()` migrates the older per-level shape (`"<clefId>:<difficultyId>"`, the levels being easy/medium/hard) by keeping the level that used to be the default, and writes the migrated shape back. The range is shown by the highlighted notes, by `.range-band` — a band drawn across them — and by `.range-letters`, the pool's note names spelled out under the staff with the in-range ones in the accent colour. The letters are what make a range readable without naming the notes off the staff first, which is the skill the game is for rather than a toll to pay in settings; each nudged `NOTEHEAD_HALF_WIDTH` (8.5px, measured off the drawn heads rather than guessed) to the right, because `getAbsoluteX()` reports a note's left edge rather than the middle of its head. They are a sibling of `.range-staff` rather than a child, since the band and the hit areas are absolutely positioned across the staff's full height and would sweep letters inside it under both. They are `aria-hidden`, because the `.range-hit` buttons already carry every note's name and whether it is in range. Still no octave numbers anywhere — the staff says which octave. Every clef's `notePool` spans the same geometry — nine diatonic steps below its middle line through eight above, i.e. 18 notes with two ledger lines either side — so a range covers the same span of notes whichever clef is showing.

**Setting a range**: the whole staff is the control. A press grabs whichever end of the range is nearer (a range collapsed onto one note opens toward the pressed note instead), and sliding drags that end from note to note; it stops at the other end rather than crossing it. Only the band moves during a drag — the staff is redrawn once, on release, by `commitRange`, which also drops an edit that changes nothing. This matters on a phone, where a note's column is only ~15px wide: the player aims with the band, not with the column. `.range-staff` is `touch-action: pan-y` so a vertical swipe still scrolls the dialog, and a gesture the browser takes over arrives as `pointercancel` and is rolled back. The `.range-hit` buttons remain one per note for the keyboard and for screen readers; the click handler behind them takes only keyboard activations (`event.detail === 0`), since a press has already applied itself by the time its click arrives.

The range staff is drawn only once it has a width. Drawing it at a fallback width while the dialog is still `hidden` widened the grid track it sits in, and the redraw on open then measured that inflated track instead of the dialog — which pushed the staff off the side of a phone screen.

**Screens**: `showScreen()` swaps between five sections. `#menu-screen` is the start screen and the hub. It carries no heading of its own — the two group labels say what is on it, and a title above them would only repeat the browser tab. One entry per *thing* the app does (`.menu-item`: an icon, a name, and a line saying what it is for), and every other screen has a way back to it: `.toolbar-back`, at the left of the toolbar opposite the settings gear, shown on every screen but the menu (the gear is pushed to the right by a `margin-left: auto` of its own rather than by the toolbar's justification, so it keeps the same corner on the menu screen, where it is the row's only child) — `showScreen()` toggles it, and like the gear it sets a `display` of its own, so `.toolbar-back[hidden]` has to spell the hiding out. It replaced a "Takaisin" button at the foot of each screen, which the games and the results never had. Escape is deliberately *not* the same: it steps out of the setup, cards and chart screens but leaves a running game alone, since a stray Escape should not walk out of a half-finished round while a deliberate click may. "Tunnista nuotit" and "Tunnista sävellaji" both lead to `#setup-screen` — the shared round-length picker — and "Nuottikortit" to `#cards-screen`. The settings are not among them: they stay behind the toolbar gear, which is on every screen including this one, so the menu lists things to play rather than mixing them with configuration. Escape steps back one level: the dialog first if it is open, then out of the cards or setup screen to the menu. A running game is deliberately left alone — there is no half-finished round to walk out of by accident.

`.main-menu` is two columns, one per subject: everything about notes on the left, everything about keys on the right, each column a `.menu-group` with its own heading. Grouping by subject rather than by kind of activity means the pairing reads down a column — game, cards, chart — instead of across. Below 600px the two groups stack, headings and all. The markup is grouped the same way, so an entry belongs to a column by where it sits rather than by counting grid cells.

**Two games, shared parts**: `gameMode` (`"notes"` / `"keys"`) says which round is running. The two share the counters (`correct`, `wrong`, `streak`, `currentIndex`, `totalNotes`), the results screen, and the round-length picker, so nearly everything that touches a running game dispatches on it: `beginGame` picks the screen and the start function, `updateStatus` writes through `statusElements()` to whichever screen's status block is showing, `redrawCurrentGame()` stands in for `renderNotation()` wherever a redraw is wanted (theme, clef, language, resize), and the keydown handler routes number keys to the key game and letters to the note game. `showSetup(mode)` sets the mode and swaps the title's `data-i18n` key, so a language change re-translates the right string. Note that `showSetup` takes an argument — a listener passed it directly would hand it a click event as the mode.

**Key signature game**: `#keys-screen`. A staff carrying only a clef and a key signature, and four answers to pick from; `KEYS` is the fifteen major keys from seven flats to seven sharps, with VexFlow's key spec (`vf`), the signed accidental count, and the tonic a right answer sounds. `keyChoices()` draws the three wrong answers from the signatures *nearest* the right one on the circle of fifths — picked from the whole circle they would mostly be a giveaway, since telling four sharps from six flats needs no reading. A question keeps its four answers while it is unanswered, so `keyQuestions[i]` holds both. The options are answered by clicking, or by 1-4 counting along them from the left — the numbers are deliberately not drawn on the buttons, being four more things to read on a screen already asking one question, so the shortcut is there for whoever finds it rather than advertised. A wrong pick is counted and costs the streak but does not advance, exactly as in the note game, so accuracy measures tries rather than skips.

The staff is sized to its content: a probe `Stave` that is never drawn reports `getNoteStartX()`, and the real one is that plus `KEY_STAVE_TRAILING`. A staff sized for seven accidentals would leave C major — a legitimate question, and a bare staff — floating in an empty field. The accidentals are tinted with `--note-current` through VexFlow's `.vf-keysignature` group, since they are what the player is being asked to read. `noteFrequency()` was widened to parse accidentals (`f#/4`, `bb/4`) so a tonic can be sounded.

**Melodies**: The round-length picker offers, under a heading of their own, seven rounds that are a tune rather than a number — all out of copyright, and all named in both languages under `melody.<id>` with their origin under `melody.<id>.source`. `MELODIES` stores each as offsets in diatonic steps from the note it opens on, paired with that note's length in beats, plus `opensOn`, the letter of the note at offset 0. An offset of `null` is a rest (Kulkuset and Piippolan vaari have them): it keeps its beats in the playback and is not a note to name, so it never reaches the staff and never counts toward `totalNotes`. They are listed narrowest span first and then shortest — the span is what makes a tune hard to read, so the list runs from Maijall' oli karitsa (five steps, 26 notes) to Jaakko kulta (nine, 32) — which is why Oodi ilolle is no longer first.

`melodyNotes(clef, melody)` places one in whichever clef is showing — the octave that puts its opening note nearest the middle staff line, of those the clef's pool can hold. **Whole octaves only**: every note of every tune is a natural and no pool has accidentals, so shifting one by anything else would change the tune rather than transpose it. Since every clef's pool spans the same 18 notes and the widest tune spans nine, all seven fit every clef today; `availableMelodies(clef)` still filters, so a narrower pool would drop a tune from the picker rather than show it dead, and `beginMelody` returns false so `restartRound()` and the Tab replay can fall back to a plain round instead of leaving one half-started.

`melodyRound` is `{ melody, entries }` while such a round is running and is what tells it apart afterwards — Tab on the results screen replays the same tune rather than a count, `restartRound()` re-places it when the clef changes, and `endGame()` plays it. The beats are used only for that playback: the staff draws every tune as plain quarter notes like any other round. `playMelody()` schedules every note on the audio clock in one go (`playPianoNote`'s `delay`) rather than chasing timers, so nothing drifts — a rest is simply silence that still takes its beats — and it waits `MELODY_LEAD_IN_SECONDS` so the note the last answer sounded has died away first. A tune is marked played under its own id rather than its length: 30 is one of the presets, and finishing Oodi ilolle should not tick it.

**Played-through marks**: The round-length picker ticks the lengths already played to the end, per game, from `playedCounts` in `localStorage` (`{ "<gameMode>": [id, ...] }`, an id being a length or a melody's id — `"ode-to-joy"` predates the other tunes and keeps working because the id it was stored under is still that melody's). `endGame()` records it, so an abandoned round does not count — the marks say what was finished, not what was attempted. `buildNoteCountOptions()` is rebuilt on every `showSetup()` (the marks differ per game, and the round just finished has to show) and on a language change (the marked buttons carry a translated `aria-label`); `buildMelodyOptions()` is rebuilt on a clef change too, since which tunes are on offer follows the clef and the dialog opens over the picker. The tick carries the meaning and the colour only backs it up, so the two states stay tellable apart without seeing the difference.

**Reference charts**: Two lookup pages rather than games, both following the clef picked in the settings and both naming that clef above the notation — a chart read in the wrong clef is worse than no chart. `#note-chart-screen` puts the current clef's whole `notePool` on one staff with every letter lit (it is a table, so nothing is picked out) — the range is deliberately ignored, since this answers "what are the notes" and not "what will the game ask". `#key-chart-screen` draws all fifteen signatures as tiles, grouped the way one is actually looked up: the sharp keys in order of how many sharps they carry, then the flat ones, with C major at the head of the sharps as nought of them rather than listed twice. Every tile is drawn on a canvas sized to `widestKeySignature()` for the same reason the key cards are — otherwise C major would come out as wide as seven sharps with its accidentals shrunk to match.

The note chart's staff is *measured*, so it has the same trap the range editor does: `showNoteChart()` renders after `showScreen()`, and the resize handler redraws it. The key chart's tiles are scaled by CSS and look after themselves. `redrawCharts()` is called from `applyTheme`, `applyClef` and `applyLanguage`, and is a no-op unless a chart is the screen showing.

`drawPoolStaff()` is what the range editor and the note chart share: it draws a clef's pool across one staff, colouring each note however the caller asks, and returns the noteheads' x positions and spacing — which is what the range band, the hit areas and the letters are all placed from. `renderNoteLetters()` is the shared letters row. Both charts reuse the `.range-*` class names for those parts, the way the clef and theme menus kept theirs; "lit" is the generic modifier that means in-range in the editor and simply "on" in the chart.

**Card decks**: Reached from the menu and left by "Takaisin" or Escape. `#cards-screen` serves two decks, chosen by `cardMode`: the clef's notes ("Nuottikortit") and the fifteen key signatures ("Sävellajikortit"). They work the same way — a staff on the front, a name on the back — so they share the screen, the flip, the stepping and the position line, and differ only in what is drawn and what is named. `cardDeck()` returns whichever list is showing; `showCards(mode)` swaps the heading's `data-i18n` key so a language change re-translates the right one. The hint is shared, because it describes the one key that works both decks rather than what is on the cards.

A deck is worked through with the space bar alone — there are no prev/next controls. `revealOrAdvance()` turns the card over, sounds it, and sets a `CARD_REVEAL_MS` timer that moves the deck on by itself; a press while the answer is up cancels that timer and steps immediately, so reading fast is never held up by it. A tap on the card does the same, for touch. The space handler calls `preventDefault()`: without it a card that has the focus would be activated a second time by the click a Space on a `<button>` leaves behind. `showScreen()` clears any pending advance, so a timer cannot fire onto a screen the player has already left.

The key deck runs outward from the middle of the circle of fifths — `keyCardOrder()` sorts by `Math.abs(accidentals)`, so C comes first and each card adds an accidental to the one before it, out to the sevens. Opening on seven flats would be teaching the hardest card first. `KEYS` itself stays in circle-of-fifths order, since that is what the table documents. Only the note deck can come out empty, so the "no notes yet" guard is note-only. Note that `showCards` takes an argument — a listener passed it directly would hand it a click event as the mode.

Each key card's front is drawn by `renderCardKeySignature()` on a canvas sized to the *widest* signature there is, measured off probe staves that are never drawn. Sizing each card to its own signature would blow a bare C major staff up to the same width as seven sharps, so the accidentals would shrink as the deck got harder; one shared canvas keeps the scale constant and lets C major be what it is — an empty signature. `scaleCardSvg()` is the step both decks share: a viewBox, no size of its own, and the inline size VexFlow writes cleared, so CSS decides how big the staff comes out.

**The note deck**: the deck is `activeNotePool()` — the current clef's pool cropped to the current range, so it is exactly the notes the game would ask about — shown **one card at a time**, big, with an arrow either side and a "Kortti 3 / 13" line beneath. `stepCard()` wraps at both ends, so no arrow is ever a dead end, and it rebuilds the card, which turns it face-up again: the next note is a new question, not the previous answer. The arrow keys leaf through the deck; Enter and Space flip, which the card gets for free by being a `<button>`. `cardIndex` survives a redraw (a theme change should not send the player back to card 1) and `renderCards` clamps it when the deck it indexes into gets shorter.

A card's front is a whole note on a miniature staff, its back the note's name; a press flips it (a CSS `rotateY` on `.note-card-inner`, faces hidden by `backface-visibility`) and plays the pitch. The back carries **letters only** — the Nordic name and, where the two differ, the international one, so `INTERNATIONAL_NAMES` maps `h` to `B` and the card reads "H / B". No octave number: the card answers "which letter is this", and a number would be a second question the game never asks.

The card staves are drawn at a fixed internal width of 150 and then stripped of their `width`/`height` — the attributes *and* the inline styles VexFlow writes alongside them, which otherwise outrank the stylesheet and pin the staff at 150px inside a card several times that wide — in favour of a `viewBox`, so CSS scales them to fill the card. That means a card can be built while the screen is still hidden; unlike the range staff, nothing here is measured. The geometry comes from `staffGeometry()` (the helper the range editor also uses) measured across the whole deck rather than the one note showing, so the staff keeps the same size and the same middle line from card to card instead of shifting under the player as they step through. Note colours are read from CSS at draw time and the deck follows both the clef and the range, so `redrawCards()` is called from `applyTheme`, `applyClef`, `commitRange` and `applyLanguage` — it is a no-op unless the deck is the screen showing.

**Settings dialog**: The gear button in the toolbar is the only always-visible control. It opens a centered modal (`#app-settings-menu`, with a backdrop) holding the language list, the clef list, the theme list and the note-range staff — all of them are set once and then forgotten, so none take up room during play. The first three sit side by side in `.app-settings-cols`. The clef and theme lists keep their `.clef-menu` / `.theme-menu` class names from when they were dropdowns of their own, and `.lang-menu` shares the clef list's rules. The sections have no visible headings — their names live on as `aria-label`s. The "← Valmis" button sits in `.app-settings-bar`, a sticky header at the top of the dialog, so it stays reachable without scrolling past the note-range staff. It is at the left of that header, wearing `.toolbar-back`'s shape and arrow: the dialog covers the toolbar, so it is the back button while it is open rather than a second control opposite it.

**Theme system**: 5 themes (2 light, 3 dark) defined as `:root[data-theme="name"]` CSS blocks. JS sets the attribute on `<html>`. The blocks are `:root`-scoped on purpose — a bare `[data-theme=…]` also matches any other element carrying the attribute, which redefines the whole palette on it; that is why the theme picker's buttons name their theme with `data-theme-id` instead. The picker's two group boxes follow the active palette like the rest of the dialog, so only their headings say which group is light and which is dark; each entry is previewed by `buildThemeChip()`, a miniature staff and note drawn in that theme's own notation colours, which `THEMES` repeats in a `chip` field since JS cannot read a palette it is not currently wearing. Theme choice persists in `localStorage` under key `"theme"`. Ids that are no longer in `THEMES` are mapped through `LEGACY_THEME_IDS` and the resolved id is written back, so each entry only has to outlive the browsers still holding it: `"dark"`/`"light"` predate the named themes, and `"nord"` was the id of `storm` (Myrsky / Storm) while it still carried the name of the palette it was drawn from.

**Input**: Keyboard only — single letter keypress triggers `handleGuess()`. No on-screen buttons for note input.
